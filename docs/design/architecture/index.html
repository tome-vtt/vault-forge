Architecture demo

Vault Forge is screens on top of one engine that holds every rule

A failed or cancelled conversion never touches your vault, two profiles share one download, and only one conversion runs at a time. The screens just ask; the engine decides.

  1. App shellNew
    The window frame: the sidebar of profiles, the top bar with the new-version notice, and the Appearance switch. It reads app settings and the release check through the Engine.
    Main functions (2, not a full list)
    • App::ui draws the frame and the current screen each frame
    • App::drain_events reads the Engine's events and updates what is shown
  2. New profile screenNew
    The first-run and New profile form: name, game rules, game data address and vault.
    Main functions (1, not a full list)
    • NewProfile::show draws the form and asks the Engine to create the profile
  3. Setup screenNew
    A profile's Setup tab: game data, books, vault, homebrew, notes switches, templates and the profile file. Shows the replace-notes confirmation before Convert.
    Main functions (2, not a full list)
    • Setup::show draws every section from the profile the Engine returned
    • Setup::confirm_convert the replace-notes question, then asks the Engine to convert
  4. Last run screenNew
    A profile's Last run tab: converting, converted and failed states, counts per folder, warnings and the log.
    Main functions (1, not a full list)
    • LastRunView::show draws the last run or the live conversion
  5. Obsidian setup screenNew
    The checklist of plugins and settings the notes need, with buttons that open plugins in Obsidian or show the bundled files.
  6. About screenNew
    Versions, licences, the unofficial notice and the source link.
  7. Engine front doorNew
    The one thing the screens ask. A few commands go in; events come out on a channel the screens read every frame. It hands each command to the part that owns it and runs long work on worker threads.
    Main functions (4, not a full list)
    • Engine::start opens the app data folder and returns the Engine and its event receiver
    • Engine::send takes one command: create, save, rename or delete a profile, download or cancel game data, convert or cancel
    • Engine::profiles the profiles to list in the sidebar
    • Event what comes back: progress, log lines, finished, failed, a newer version
  8. ProfilesNew
    Creates, saves, renames and deletes profiles. Each profile is a converter config file plus the few settings the converter does not read (the game data address, the images switch).
    Main functions (3, not a full list)
    • Profiles::create a new profile from a name, rules, address and vault
    • Profiles::save writes a change at once
    • Profiles::delete removes the profile and releases its game data
  9. Game dataNew
    Downloads, unpacks and updates the game data for an address, and reads its book list. Keeps one copy per address in the data cache and removes it when no profile uses it. Refuses a download with no books list.
    Main functions (3, not a full list)
    • GameData::check asks whether newer data exists, without downloading
    • GameData::download downloads and unpacks, with progress events; images are a second download
    • GameData::books the books grouped into core rules, supplements and adventures
  10. ConversionNew
    Runs one conversion at a time across the app. Writes into a holding folder, and only on exit code 0 swaps the compendium and rules folders into the vault. Failure or cancel discards the holding folder, so the vault is never half updated.
    Main functions (3, not a full list)
    • Conversion::start refuses if one is running, then runs the converter
    • Conversion::cancel stops the converter and discards the holding folder
    • Conversion::explain turns an exit code into one plain sentence and a fix
  11. Last runNew
    Keeps only the latest record per profile: notes counted per output folder, warnings and the full log.
    Main functions (2, not a full list)
    • LastRun::save replaces the profile's record
    • LastRun::load the record the Last run tab shows
  12. Release checkNew
    Looks up the newest release of Vault Forge on GitHub and reports a newer version. It never installs anything.
  13. App settingsNew
    Settings that belong to the app, not a profile: the appearance choice (System by default) and the last profile opened.
  14. Profile filesNew
    Reads and writes each profile's converter config file and its last-run record in the app data folder.
  15. Settings fileNew
    Reads and writes the app settings.
  16. Data cacheNew
    The folder of unpacked game data, one folder per download address.
  17. DownloaderNew
    Fetches files over HTTPS with progress, for game data and for the release check.
  18. ConverterNew
    Starts the bundled converter program, streams its output line by line and reports its exit code.
  19. Holding folderNew
    Creates the holding folder, swaps its compendium and rules folders into the vault, or discards it.

What happens, step by step

One conversion of a profile that already has notes in its vault, from pressing Convert to the Last run tab.

sequenceDiagram
  actor GM
  participant setup as Setup screen
  participant engine as Engine front door
  participant conversion as Conversion
  participant profiles as Profiles
  participant gameData as Game data
  participant holding as Holding folder
  participant converter as Converter
  participant lastRun as Last run
  GM->>setup: Press Convert, then confirm replacing notes
  setup->>engine: convert(profile)
  engine->>conversion: start(profile)
  conversion->>conversion: Refuse if another conversion is running
  conversion->>profiles: Read the profile's config
  conversion->>gameData: Locate the profile's game data in the data cache
  conversion->>holding: Create an empty holding folder
  conversion->>converter: Run with the config, writing into the holding folder
  converter-->>conversion: Log lines and warnings as they print
  conversion-->>engine: Progress events
  engine-->>setup: Step, elapsed time, live log
  converter-->>conversion: Exit code 0
  conversion->>holding: Swap compendium and rules folders into the vault
  conversion->>lastRun: Save counts per folder, warnings and log
  conversion-->>engine: Finished event
  engine-->>setup: Show the Last run tab with the result
  1. The GM presses Convert on the Setup screen and confirms that the converted notes will be replaced.
  2. The Setup screen asks the Engine to convert the profile; the Engine hands it to Conversion.
  3. Conversion refuses if another conversion is already running anywhere in the app.
  4. It reads the profile's config from Profiles and finds the profile's game data in the data cache.
  5. It creates an empty holding folder and runs the converter with the config, writing into that folder.
  6. Every log line and warning streams back through the Engine to the screen as it prints.
  7. On exit code 0, the holding folder's compendium and rules folders replace the vault's. Nothing else in the vault is touched.
  8. Conversion saves the last run (counts per folder, warnings, log) and the screen switches to the Last run tab.
  9. On any other exit code, or a cancel, the holding folder is thrown away and the vault stays exactly as it was.

Your layer rules

  • Calls only go downward: screens ask the Engine, the Engine uses storage and tools, nothing calls upward.
  • No layer is skipped: no screen reads a file, downloads anything or runs the converter itself.
  • Every rule lives in the Engine, once: one conversion at a time, hold then swap, one shared copy per address, refusing a download that is not game data.
  • Storage and tools hold no rules; they only read, write, fetch and run.
  • No rule needed breaking.
